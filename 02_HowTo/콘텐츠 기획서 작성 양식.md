> 콘텐츠 개발 문서(기획서)의 표준 작성 양식. 개발 담당자(기획자, 프로그래머, 아티스트)가 빠르게 파악하도록 개요 → 전체 플로우 → 공용 시스템 → 개별 시스템 순으로, 시스템 단위로 묶어 구성함. 화면의 시각과 레이아웃 상세는 별도 UI 문서가 다루고, 그 화면이 받는 입력과 판정 로직은 본 문서에 둠.

# 1. 목적과 독자

- 목적: 콘텐츠별 기획서를 일관된 뼈대로 써서 개발 담당자가 30초 안에 구조를 잡고 자기 관심 부분으로 바로 이동하게 함
- 독자별 관심: 기획자는 동작과 규칙, 프로그래머는 입력과 출력 및 기술 요건, 아티스트는 필요 리소스
- 적용: 시범콘텐츠 콘텐츠 개발 문서 전반. 세션과 Step 골격은 [[시범콘텐츠 공통 사양]], 1년차 사용자 모델은 [[플랫폼 사양#5. 사용자 모델 (1차연도)]]을 인용함 (연속성은 2차연도 [[플랫폼 사양#6. 2차연도 전방 설계 (디지털 도제 연속성, 현재 구현 밖)]])
- 플랫폼 차이: 1년차는 키오스크(1인) 중심이고 사용자 모델은 익명 1회성임([[플랫폼 사양#5. 사용자 모델 (1차연도)]]). 미디어 케이브(다중)의 사용자 식별과 누적은 1년차 범위 밖이며 2차연도 미정임

# 2. 문서 범위

- **포함**: 콘텐츠 로직. 런타임 흐름과 그 상태, 분기, 병행, 파기 시점, 시스템과 그 동작과 규칙, 기술 요건, 필요 리소스, 가드레일, 그리고 화면이 받는 입력과 판정과 상태 로직
- **제외**: 화면의 시각과 레이아웃 상세(배치, 컴포넌트 디자인, 비주얼)는 별도 UI 개발 문서가 정본임. 단 화면이 받는 입력, 판정, 상태, 개인정보 처리 같은 인터랙션 로직은 UI 장식이 아니라 콘텐츠 로직이므로 본문에 남김
- **참조로 대체**: 세션과 그 개인정보 공통 원칙은 [[시범콘텐츠 공통 사양#8. 개인정보와 가드레일 원칙]], 1년차 사용자 모델은 [[플랫폼 사양#5. 사용자 모델 (1차연도)]](연속성과 프로필 개인정보는 2차연도 [[플랫폼 사양#6. 2차연도 전방 설계 (디지털 도제 연속성, 현재 구현 밖)]]), 공통 기술 방향(회의 근거)은 [[시범콘텐츠 공통 사양]]을 인용함. 콘텐츠 고유 데이터와 개인정보(영상, 사진, 콘텐츠 결과물 등)는 참조로 대체하지 않고 본문 시스템에 둠

# 3. 표준 목차

시스템 단위로 묶는 목차임. 레이어별(구성 요소, 기술 구성, 파라미터)로 흩어져 한 시스템을 보려면 문서 여기저기를 뒤져야 하던 현행 불편을 없앰. 아래 절 번호는 작성 대상 콘텐츠 기획서의 절을 가리킴 (이 양식 문서 자신의 절 번호와 구분).

| 절         | 내용                                                                                                                                                                                      | 정렬                 |
| --------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------ |
| 1. 개요     | 한 줄 정의, 소재, 목표 경험, 핵심 메커닉, 산출물. 이 5항목만 둠. 디바이스는 콘텐츠 정의에 "키오스크 콘텐츠"처럼 흡수하고, 플랫폼과 세션, 유형, 성격(학습 도구나 연속성) 불릿은 개요에 두지 않음([[#가. 불변식 (반드시 지킴)]] 3). 각 항목에 괄호를 쓰지 않음. 약어 첫 등장 병기만 예외([[#가. 불변식 (반드시 지킴)]] 4)                    | 현행 유지              |
| 2. 전체 플로우 | Step 시퀀스 한 줄과 큰 분기만 그림. 세션 진행과 갈림을 한눈에 잡게 함. 분기는 이탈(유저 그만두기, 타임아웃, 위반 한도 초과)과 실패(생성이나 전달 실패, 무응답) 두 갈래로 나눠 적음. 내부 판정 로직은 배제(로직은 3절 시스템과 4절 Step에). 실시간이나 동시 구간은 번호 순서에 욱여넣지 않고 병행이나 루프로 묶어 표기. 공통 사양 임베드는 쓰지 않음(임베드는 Obsidian 밖에서 안 펼쳐져 외부 제출본이 빔) | Step 진행 순      |
| 3. 공용 시스템 | 2개 이상 Step에서 쓰이는 기능과 횡단 정책(가드레일, 세션과 개인정보). 각 시스템은 본 양식 [[#나. 시스템 독립 명세 양식]] 형식으로 씀. 튜닝값(임계, 재시도, 타임아웃 등)은 그 시스템 안에서 쓰이는 지점에 실제 잠정값과 근거로 인라인 표기함([[#나. 설계 원칙]])                                    | 콘텐츠 공용 먼저, 내부 공용 나중 (묶음 내 의존 순, [[#가. 정렬 원칙]]) |
| 4. 세션 진행 | Step을 순서대로 담는 H1 절. **각 Step은 그 아래 H2**(`## 가. Step 1. 인트로`)임. Step 안의 진행 단위(UI 화면, 서버, 백그라운드와 포그라운드 등)가 H3이고 진행과 분기는 H4임. 공용이 아닌 엔진(생성, 변환, 채점 등)은 자기를 부르는 진행 단위 아래 H4로 두고 명세 항목을 H5로 붙임. 진행 단위는 진행과 분기만 적고, 독립 명세가 필요한 엔진만 [[#나. 시스템 독립 명세 양식]] 형식으로 자기 완결하게 씀 | Step 진행 순 |
| 5. 운영 기준 | 운영과 구현이 참고할 값과 케이스를 모음. **가. 운영 파라미터**는 각 시스템에 인라인한 잠정값을 한자리에 모은 색인 표임(값의 정본은 각 시스템 본문, [[#나. 설계 원칙]] 튜닝값 인라인). **나. 에러 케이스**는 런타임에 터질 수 있는 실패를 전수로 모은 표임([[시범콘텐츠 공통 사양#라. 에러 케이스 표 (각 기획서가 씀)]]) | 파라미터 → 에러 케이스 |
| 6. 관련 문서 | UI 문서, 공통 사양, 플랫폼 사양 등. Step 수와 무관하게 마지막 H1임(Step이 4절 안에 묶이므로 절 번호가 밀리지 않음) | 현행 유지 |

## 가. 불변식 (반드시 지킴)

1. **흐름과 로직 분리**: 흐름(시퀀스와 분기)은 2절 전체 플로우에만, 내부 판정 로직은 3절 공용 시스템과 4절 세션 진행의 엔진에만. 같은 내용을 두 곳에 중복 서술하지 않음
2. **공용과 개별 경계 테스트**: 2개 이상 Step에서 쓰이면 공용(3절), 한 Step에서만 쓰이면 그 Step 안의 엔진(4절). 단 횡단 정책(가드레일, 세션과 개인정보)은 사용 횟수와 무관하게 공용
3. **개요 금지 항목**: 개요는 한 줄 정의, 소재, 목표 경험, 핵심 메커닉, 산출물 5항목만 둠. 디바이스는 별도 불릿으로 빼지 않고 콘텐츠 정의에 "키오스크 콘텐츠"처럼 흡수함. 플랫폼과 세션은 전체 플로우와 공용 시스템(세션 데이터)에, 유형은 콘텐츠 정의 문구에, 학습 도구나 재방문 연속성 같은 성격은 관련 시스템(채점, 개인정보)에 두고 개요에는 두지 않음. 옛 기획서를 참고해 이 불릿들이 딸려오지 않게 함
4. **개요 괄호 금지**: 개요 5항목에는 괄호를 쓰지 않음. 개요는 콘텐츠의 뼈대만 세우는 자리임. 괄호 내용은 뼈대가 아니고 상세 절과 중복됨
	- **금지 예**: 같은 대상을 딴 이름으로 다시 부르기("덜미(꼭두각시놀음)를 소재로 한"), 속성이나 형식 덧붙이기("전자책(인형 시각 정체성 유지, 세로 형식)"), 구성 요소 열거하기("문학적 골격(재담, 풍자, 거리식 구성)은 고정하고")
	- **개요의 유일한 예외**: 약어 첫 등장 시 본디 용어 병기("증강현실(AR)"). 괄호가 없으면 약어를 못 읽으므로 위키 작성 규칙의 쉽게 쓰기 원칙이 우선함. 약어가 아닌 이칭 병기는 위 금지 예 첫째에 해당함
	- **뺀 내용의 행선지**: 소재 설명은 소재 페이지, 동작과 규칙은 해당 시스템 절, 화면 형식은 UI 문서로 보냄. 개요로 되돌리지 않음

## 나. 설계 원칙

- 전체 플로우는 세션과 Step 흐름을 한눈에 보여주고(시퀀스와 분기만), 시스템 절은 각 시스템의 런타임 명세(역할, 입출력, 동작과 규칙, 기술 요건 등)를 담음
- 상태와 분기, 병행, 실패는 흐름도나 상태 표기로 명시하되 시각 디자인은 적지 않음
- 산출물, 일정과 마일스톤, 리스크와 검증 절을 현행 표준 목차에서 뺌. 산출물은 개요와 각 시스템 출력으로, 일정과 리스크는 별도 관리 문서로 다룸
- **적용 범위**: 아래 참조 집약, 튜닝값 인라인, 자족성 규칙은 콘텐츠 기획서 결과물의 본문 절 전체(개요부터 운영 기준까지)에 적용함. 본 양식이나 운영 규칙 문서 자체는 대상이 아님(그 문서들은 위키링크를 정상 사용함)
- **참조 집약**: 결과물 본문에서 타문서 위키링크와 "참고/참조"를 걷어 관련 문서 절로 모음. 시스템을 가리킬 때는 § 번호 없이 시스템 이름을 평문으로 씀(예: "실패 처리 경로에 합류", "가드레일(런타임 입력)"). 링크가 본문에 흩어져 독자가 파악하려 문서를 왔다갔다 하는 것을 막음
	- **예외 (비-시스템 절 참조)**: 운영 기준의 운영 파라미터와 에러 케이스는 시스템이 아니라 표라서 이름만으로는 어디를 보라는 건지 알기 어려움. 이때만 `§5.나 에러 케이스`처럼 절 번호와 이름을 함께 씀([[CONVENTIONS#마. Wikilink 규칙]] § 참조에 헤더 이름 병기)
- **튜닝값 인라인**: 임계, 재시도 횟수, 타임아웃, 길이 제한, 생성 튜닝값(temperature 등) 같은 값은 쓰이는 지점에 실제 잠정값과 근거를 적음(예: "임계 60초(잠정)", "위반 3회(잠정) 시 종료"). 공통 기본값이 공통 사양에 있으면 그 콘텐츠에 적용하는 값을 인라인으로 옮겨 적고(공통과 다르게 잡으면 그 근거를 붙임), 출처만 관련 문서로 둠. 지금 못 정하는 품질 지표(오탐율 등 검증 데이터가 있어야 정하는 값)만 "정량 미정"으로 남김
	- **값의 정본은 시스템 본문임**. 운영 기준의 운영 파라미터 표([[#3. 표준 목차]] 5절)는 그 값을 한자리에 모은 색인이지 정본이 아님. 본문 없이 표에만 값을 두지 않음
- **자족성**: 각 명세 항목은 그 자리에서 이해되게 씀. 실패와 복구를 "한도 초과 시 폐기"처럼 던지지 말고, 무엇이 실패하고 누가 어떻게 처리하는지까지 적음
- **모델과 엔진 구분**: 설계 모델(규칙과 틀)과 그것을 돌리는 생성 엔진을 다른 시스템으로 나눔. 모델의 역할과 목적은 "규칙을 정의함"(직접 생성 안 함)이고, 엔진은 "그 규칙으로 실물을 생성함"임. 모델은 여러 엔진과 시스템의 공용 기반이 되기도 하므로 엔진에 합치지 않음

# 4. 시스템 작성법

## 가. 정렬 원칙

절별 배열은 [[#3. 표준 목차]]를 따름: 엔진(4절 세션 진행)은 그 엔진을 부르는 Step과 진행 단위 순, 공용 시스템([[#3. 표준 목차]])은 쓰임 범위로 두 묶음을 나눠 정렬함. 여러 콘텐츠가 공유하는 기능을 앞에, 그 콘텐츠 안에서만 공용인 기능을 뒤에 두고, 각 묶음 안에서는 의존 방향 순(많이 의존받는 기반부터)으로 정렬함.

1. **콘텐츠 공용 (앞)**: 여러 콘텐츠가 공유하는 횡단 기능. 대개 공통 사양이 정의하는 골격임. 예: 세션과 개인정보, 진행 호스트, 진행 중 종료와 타임아웃, 입력 유효성 검증, AI 가드레일, 외부 서비스 호출 래퍼, 실패 처리
2. **콘텐츠 내부 공용 (뒤)**: 그 콘텐츠 안에서 여러 Step이 공유하는 고유 시스템. 예: 설계 모델(서사 규칙과 틀 등)과 그 모델로 플롯 풀을 사전 생성하는 엔진. 런타임 생성 엔진(입력 가공, 이미지 생성, 조립 등)은 여기가 아니라 4절 세션 진행의 해당 Step에 둠

각 묶음 안에서는 다른 시스템이 전제로 삼는(많이 의존받는) 기반부터 두고, 그것을 쓰는 시스템을 뒤에 둠. 한 엔진과 그 입력 데이터처럼 강하게 묶인 시스템은 인접 배치함. 의존 관계는 별도 항목이 아니라 입력과 출력이나 동작과 규칙 안에서 필요한 만큼만 밝힘.

## 나. 시스템 독립 명세 양식

기획서에서 각 시스템은 헤더로 두고 그 아래 명세 항목을 정해진 순서의 서브헤더로 씀. 헤더 레벨은 위치를 따름:

- **공용 시스템([[#3. 표준 목차]])**: 시스템이 H2(`## 가. 시스템 이름`), 명세 항목이 H3(`### 1) 역할과 목적`)
- **개별 시스템(§4 세션 진행)**: 세션 진행이 H1(`# 4. 세션 진행`), 각 Step이 H2(`## 가. Step 1. 인트로`)임. Step 안의 진행 단위(UI 화면, 서버, 백그라운드와 포그라운드 등)가 H3(`### 1) UI(시작 화면)`)이고, 각 진행 단위 아래 진행과 분기는 H4(`#### 가) 진행`)로 적음. UI나 서버 진행 단위는 진행과 분기만 적고 명세 항목을 붙이지 않음. 독립 명세가 필요한 엔진은 그 진행 단위 아래 H4(`#### 나) 엔진 이름`)로 두고 명세 항목을 H5(`##### (1) 역할과 목적`)로 붙임
	- 엔진 헤더에는 이름만 씀. "(개별 시스템)" 같은 꼬리표를 붙이지 않음(붙이는 엔진과 안 붙이는 엔진이 갈리면 독자가 다른 종류로 오해함)
	- 엔진 명세가 H5까지 내려가므로 깊이 한계에 닿음([[CONVENTIONS#4. 헤딩 / 넘버링]]). 엔진의 동작과 규칙에 하위 분류가 필요하면 헤더를 더 파지 말고 서브불릿이나 표로 풂

볼드 라벨 불릿이 아니라 헤더인 이유: 항목마다 규칙이 여럿이거나 표가 들어가 길어지므로, 헤더라야 표와 서브불릿을 깔끔히 담고 목차에 잡힘 ([[반복 결함 카탈로그]] STRUCT-007). 항목 순서가 늘 같아 독자가 자기 관심 항목으로 바로 건너뜀(프로그래머는 입출력과 기술 요건을, 기획자는 동작과 규칙을, 아티스트는 필요 리소스를 봄).

### 1) 명세 항목과 순서

아래 순서로 씀. "필수"는 모든 시스템에 두고, 조건부 항목은 괄호의 대상에 해당할 때만 두며 해당 없으면 그 헤더를 통째로 생략함("해당 없음"으로 채우지 않음). 생략해도 남은 항목을 1)부터 순서대로 다시 번호매김함(헤딩 넘버링 끊김 방지).

1. **역할과 목적** (필수): 이 시스템이 맡는 역할과 왜 존재하는가(목적). 기능이나 동작 서술("~함")이 아니라 역할 + 목적임. 예: "유저 입력을 검사함"(기능만)이 아니라 "입력을 걸러내는 관문 역할로, 잘못된 입력이 생성과 전달을 깨뜨리지 않게 하는 게 목적"(역할 + 목적)
2. **입력과 출력** (조건부, 데이터를 주고받는 시스템): 받는 데이터와 내는 데이터, 형식과 규격. 입출력 배선을 여기서 밝히므로 별도 의존 항목을 두지 않음
3. **동작과 규칙** (필수): 핵심 로직과 판정 규칙. 규칙이 여럿이면 서브불릿이나 표로 풂. 하위 분류가 여럿이면 공용 시스템에서는 H4(`#### 가) …`)로 나누고, 엔진(§4 세션 진행 안)에서는 이 항목이 이미 H5라 헤더 대신 서브불릿이나 표로 풂(H5가 깊이 한계, [[CONVENTIONS#4. 헤딩 / 넘버링]])
4. **기술 요건** (조건부, AI나 엔진 시스템): 무슨 기술로 만들고, 무엇을 결정해야 하며, 품질을 뭘로 재는지. 프로그래머가 "뭘 만들고 뭘 정해야 하는지" 읽히게 씀(방향만 던지지 않음). 역할과 목적, 입출력, 실패와 복구는 이 항목이 아니라 각 명세 항목이 소유함. 값은 인라인으로 적고 본문에 "참고" 링크는 남기지 않음
	- **모델 확보** (필수): 자체 학습, 사전학습 모델, 외부 API, 파인튜닝 중 방식. 규칙 기반 모듈은 규칙 정의 방식으로 적음(후보나 미정은 확인 필요)
	- **판정 기준** (필수): 무엇으로 품질을 재는가(예: 화자 일관성, 양식 정합, 응답 시간). 수치는 검증 데이터가 있어야 정해지므로 "정량 미정"으로 남겨도 됨(임의 추정 금지)
	- **적용** (필수): 실시간인가 배치인가, 서버인가 온디바이스인가, 어느 Step에서 부르는가
	- **생성 튜닝값** (조건부, 생성 엔진): temperature 같은 값은 결과물 성격을 좌우하는 설계 결정이라 잠정값을 인라인으로 적음([[#나. 설계 원칙]] 튜닝값 인라인). 구현 코드와 세부 하이퍼파라미터 표는 설계 단계 몫이라 적지 않음
	- **데이터** (조건부, 학습이나 레퍼런스 데이터가 필요한 시스템): 무슨 데이터로 만들고 무엇으로 검증하는가. 외부 API나 사전학습 모델을 그대로 쓰는 엔진은 이 필드를 생략함(학습 데이터가 없음)
5. **필요 리소스** (조건부, 비주얼이나 음성 자산이 있는 시스템): 구현에 필요한 입력 자산(레퍼런스, 화법, 보이스 등)과 규격을 여기 적고, 제작 발주 상세와 납품 규격은 발주 문서에 둠. facet 이름은 "필요 리소스"로 통일함(다른 이름 쓰지 않음)
6. **실패와 복구** (조건부, 실패 양상이나 가드레일이 있는 시스템): 무엇이 실패하고 누가 어떻게 처리하는지 자족적으로 적음. 적용 가드레일도 밝힘(가드레일 정의 자체는 §3 공용 시스템에). AI나 엔진 시스템은 AI 특유의 실패 조건(저신뢰, 오탐, 미탐, 타임아웃)과 재시도, 한도, 대체 경로(fallback)를 반영하고 해당 Step의 실패 분기와 연결함

**의존 항목은 두지 않음**: 시스템이 무엇에 연결되는지 되짚는 역방향 링크나 입출력 중복이라, 본문을 왔다갔다 하게 만들고 새 정보도 없음. 시스템 간 연결은 입력과 출력(배선)과 각 시스템이 자기 자리에서 밝히는 적용 관계로 충분함. 시스템 배열 순서는 여전히 의존 방향을 따름([[#가. 정렬 원칙]]).

### 2) 상호참조와 앵커

결과물 기획서 본문에서 다른 시스템을 가리킬 땐 § 번호 없이 시스템 이름을 평문으로 씀(참조 집약, [[#나. 설계 원칙]]). 시스템 이름 헤더가 고유해 이름만으로 충분하고, 같은 명세 항목 헤더(동작과 규칙 등)가 시스템마다 반복돼도 참조 대상은 시스템 이름이라 문제없음. 특정 항목을 지목해야 하면 블록 ID(`^id`, wiki_lint 지원)를 씀. (본 양식 문서가 절을 지목할 때 쓰는 `§4.다`식 표기는 이 양식의 상호참조 방식이지, 결과물 본문 표기가 아님.) 중첩 헤더 경로(`#시스템#항목`)는 Obsidian이 지원하나 현재 lint가 미검증이라 쓰지 않음(lint 확장은 후속 과제).

### 3) 기획서 적용 예

공용 시스템([[#3. 표준 목차]])은 시스템이 H2, 명세 항목이 H3임.

```
## 다. 묘기와 재담 채점
### 1) 역할과 목적
### 2) 입력과 출력
### 3) 동작과 규칙
#### 가) 채점 입력
#### 나) 난이도 상승
### 4) 기술 요건
### 5) 실패와 복구
```

개별 시스템의 엔진은 세션 진행(H1) 아래로 두 단계 더 깊음.

```
# 4. 세션 진행
## 라. Step 4. 결과물 생성과 대기 화면 (병행)
### 1) 백그라운드: 결과물 생성
#### 가) 진행
#### 나) 이미지 생성 모델
##### (1) 역할과 목적
##### (2) 입력과 출력
##### (3) 동작과 규칙
##### (4) 기술 요건
##### (5) 필요 리소스
##### (6) 실패와 복구
```

## 다. 시스템 입도

- 한 시스템은 독립적으로 설계, 구현, 검증되는 단위로 잡음
- 너무 잘게(한 줄로 끝날 만큼) 쪼개거나, 서로 다른 메커닉을 한 블록에 뭉치지 않음 ([[반복 결함 카탈로그]] STRUCT-005)
- 헤더만 두고 내용을 비우지 않음. 역할과 목적, (있으면) 입출력, 동작까지 적어 보고 무엇을 만들지 알게 함. 입출력은 조건부라 없는 시스템(정책이나 타임아웃 등)도 있음 (CONTENT-002)

## 라. 운영 기준 작성법

기획서 5절(운영 기준)에 두는 두 표의 작성 규칙임. 둘 다 값이나 케이스를 한자리에 모으는 색인이며, 정본은 각 시스템 본문임.

### 1) 운영 파라미터 표

각 시스템에 인라인한 잠정값을 구분, 파라미터, 잠정값, 적용 위치 네 열로 모음. 구현과 운영 단계에서 조정할 대상을 한눈에 보는 게 목적임.

- 표에만 있고 본문에 없는 값을 두지 않음. 값의 정본과 도출 근거는 시스템 본문임([[#나. 설계 원칙]] 튜닝값 인라인)
- 공통 사양에 공통 기본값이 있으면 그 콘텐츠가 실제 적용하는 값을 적음. 공통과 다르게 잡으면 시스템 본문에 근거를 붙임

### 2) 에러 케이스 표

런타임에 터질 수 있는 실패를 전수로 모음. 발생 지점, 처리, 원인, 팝업, 이후 동작 다섯 열로 씀. 개발자가 어떤 실패에 무엇을 띄우고 어디로 보내는지 한 표에서 보게 하는 게 목적임.

- **처리 (세션에 미치는 영향)**: 재입력(유저 입력만 다시 받으면 이어 감), 대체 입력(입력 수단을 바꿔 이어 감), 기능 축소(보조 기능만 빼고 이어 감), 중단(결과물이 남지 않아 종료) 넷으로 나눔
- **원인 (실패가 누구에게서 비롯됐나)**: 유저, 외부 서비스, 시스템 셋으로 나눔. **운영 알림 여부가 이 열에서 바로 나옴**(외부 서비스나 시스템이면 알림 대상, 유저면 비대상). 알림 열을 따로 두지 않음(원인 열과 중복)
- 유저가 스스로 고르는 그만두기는 정상 종료라 에러 케이스가 아님. 타임아웃도 이탈 대응이라 넣지 않음
- 갈래를 나누는 판정 규칙은 실패 처리 시스템(3절)이 소유하고, 이 표는 그 규칙을 케이스에 적용한 결과임. 같은 케이스를 두 곳에서 열거하지 않음([[반복 결함 카탈로그]] CONTENT-003 순환 참조)
- 화면 문구(팝업 제목과 본문)를 이 표에 담을지는 콘텐츠가 정함. 문구는 5종이 공유하므로 공통 사양으로 올리는 것도 방법임

# 5. 명료성과 명명

구조를 잡아도 문장이 어려우면 안 읽힘. 아래는 [[플랫폼 사양]]과 [[시범콘텐츠 공통 사양]]을 쓰며 반복 발견된 결함을 기획서 작성 규칙으로 정리한 것임. 문체 정본은 [[CONVENTIONS#2) 쉽게 쓰기]]와 [[CONVENTIONS#아. 구조 우선 작성 (정보 설계)]]이고, 본 절은 그 기획서 적용분임.

## 가. 평이화 (전문용어와 번역 투 배제)

- 요구공학이나 구현 전문용어를 일상어로 풂. 예: "인터페이스 계약" → "콘텐츠가 공통 엔진에 넘기는 설정 필드", "저장 스키마 경계" → "어떤 값이 들어가는지", "소비 계약" → "다른 단계가 이 결과를 조회하고 받아 쓰는 방식", "리그" → "애니메이션 가능한 캐릭터 본체"
- 즉석 조어를 만들지 않음. 뜻이 모호한 신조어(예: "런타임 경계")나 오해를 부르는 말(예: "강등" → "음성 없이 텍스트로 낮춰 진행")은 풀어 씀
- 약어는 첫 등장 시 본디 용어를 병기함

## 나. 명명 정합

- 절 제목이 본문 내용을 정확히 가리키는가. 어긋나면 바꿈 (예: 왜 개발하는지를 담은 절 제목이 "RFP 추적"이면 "개발 근거"로)
- 한 이름이 두 뜻으로 읽히면 더 구체적인 이름으로 바꿈 (예: "사용자 모델"이 저장 데이터와 학습 개인화 둘로 읽힘)
- 같은 개념은 문서 전체에서 한 용어로 통일함
- 정의는 순환하지 않게 씀(A를 B로, 다시 B를 A로 정의 금지). 다른 곳에서 빌려온 개념은 그 자리에서 인라인으로 정의함

## 다. 자족성

- 표 셀에 "동일", "상동"처럼 윗행을 되짚어야 아는 표기를 쓰지 않음. 실제 값으로 채워 표만 스캔해도 알게 함
- 임베드되거나 참조되는 블록 안의 자기 문서 § 번호 참조는 절 이름이나 절대 wikilink로 자족화함 ([[CONVENTIONS#마. Wikilink 규칙]])
- 헤더만 두고 내용을 비우지 않음 ([[#4. 시스템 작성법]]다와 같은 원칙, [[반복 결함 카탈로그]] CONTENT-002)

## 라. 구조 정합

- 순차가 아닌 것을 순차 단계로 넣지 않음. 시점이 고정되지 않는 이벤트(동의 변경이나 철회 등)는 순차 플로우에서 빼 "시점 무관 이벤트"로 분리함
- 유저 입력 재시도(비속어나 가드레일 위반으로 재입력) 분기는 무한 반복을 막게 한도(예: 3회)와 초과 처리(종료 등)를 명시함. 시스템 실패(상황 안내 뒤 종료)는 실패 처리로, 유저가 유효 입력을 못 준 소진은 로컬 종료로 성격을 나눔
- 여러 콘텐츠에 반복되는 공통 패턴(예: AI 생성이나 변환 대기)은 개별 기획서가 아니라 [[시범콘텐츠 공통 사양]] 공통 절로 올리고, 기획서는 콘텐츠 고유분만 둠
- 개발 본문에 위키 작성 메타(인용 규칙, 작성 규칙 링크 등)를 섞지 않음. 필요하면 부록으로 격리함

## 마. 표기

- "법무" 대신 "규정 검토"로 씀 (회사에 법무팀이 없어 "법무 검토"가 없는 팀을 전제하는 것처럼 읽힘)
- 가운뎃점과 em dash 금지 등 표기 정본은 [[CONVENTIONS#라. 문체]]

## 바. 낯선 독자 검토 (작성 후 점검)

가~마는 작성 규칙, 본 절은 그 적용을 확인하는 점검 절차임 (규칙과 절차를 분리함). 점검은 자기 점검만으로 끝내지 않고 독립 검토까지 두 단계로 함.

- **1차 자기 점검**: 가~마를 적용해 쓴 뒤, 자기가 쓴 문장을 맥락 없이 다시 읽음. 모든 용어가 정의됐는지, 처음 보는 사람이 한 번에 이해하는지, 같은 말을 반복하지 않는지 확인함
- **2차 독립 검토**: 작성자는 자기 의도를 이미 알아 1차만으론 의미 결함을 놓치므로, 새로 쓰거나 고친 정본 문장은 맥락 독립 검토를 1회 거침
	- 작은 변경은 깨끗한 컨텍스트의 서브에이전트가 검토함
	- 큰 변경이나 외부 노출 문서는 Codex 가독성 발췌가 검토함
	- 독립 검토를 통과하기 전에는 "검수 완료"로 표시하지 않음 ([[AGENTS#나. 역할별 호출 절차]])

# 6. 현행에서 신양식으로 매핑

기준 구현은 [[덜미 - 나만의 유람기 기획서]]임. 본 양식은 그 기획서의 구조를 표준으로 삼아 쓰였고, 나머지 4종은 2026-07-14에 신양식으로 재작성을 마쳐 5종이 같은 구조를 씀. 아래 매핑은 구양식 문서를 신양식으로 옮길 때 쓴 기준이며, 앞으로 다른 콘텐츠를 옮길 때도 같게 적용함.

| 현행 위치 | 신양식 위치 |
|---|---|
| [[#2. 문서 범위]] 시스템 플로우와 동작의 Step별 명세 | 2. 전체 플로우 (Step 시퀀스와 이탈/실패 분기만, 내부 로직은 시스템으로) |
| [[#3. 표준 목차]] 콘텐츠 설계(진행 호스트, 메커닉, 자산, 가드레일) | 3. 공용 시스템 / 4. 세션 진행 (시스템별 독립 명세) |
| [[#4. 시스템 작성법]]와 [[#5. 명료성과 명명]] 기술 구성(AI 등) | 각 시스템의 "기술 요건" 항목으로 통합 (공용은 3절, 엔진은 4절 Step 안) |
| Step 명세 안의 화면 | 본문에서 제거, UI 문서로 분리 (플로우에서 참조만) |
| 세션, 개인정보, 연속성 | 3. 공용 시스템(횡단), 공통 골격은 공통 사양과 플랫폼 사양 참조 |
| 흩어진 잠정값과 실패 분기 | 5. 운영 기준 (운영 파라미터 색인 표, 에러 케이스 전수 표) |

**구양식과의 차이**: 구양식은 Step이 H3(`### 1) Step 1.`)이고 공통 사양 임베드(`![[ ]]`)를 썼음. 신양식은 Step이 H2이고 임베드를 쓰지 않음. 재작성 시 이 두 지점을 함께 고침.

시스템 정렬 예시 (의존 방향 순):
- 덜미 유람기(기준 구현): [[시범콘텐츠 공통 사양#3. 공용 기능]]은 콘텐츠 공용을 앞에 두고(세션 데이터 → 개인정보 처리 → 언어 선택 → 진행 호스트 → 진행 중 종료 → 화면 타임아웃 → 터치 미입력 타임아웃 → 입력 유효성 검증 → AI 가드레일 → 외부 서비스 호출 래퍼 → 실패 처리), 콘텐츠 내부 공용을 뒤에 둠(서사 구조 규칙 모델 → 그 규칙으로 플롯 풀을 사전 생성하는 마당 플롯 생성 LLM). 런타임 생성 엔진(유저 입력 가공 LLM, 이미지 생성 모델, 낭독 음성 생성, 결과물 조립)은 4절 세션 진행의 Step 4 안, 그 엔진을 부르는 진행 단위(백그라운드) 아래에 둠. 자산과 인프라는 별도 시스템 절로 두지 않음(발주 자산은 발주 문서, 플랫폼 인프라는 플랫폼 사양 영역)
- 덧뵈기 탈춤: 1) 탈과 춤사위 고증(공통 레퍼런스)과 탈 디자인 도구 2) 탈 3D 변환 3) 포즈 채점과 신명 게이지(핵심 메커닉) 4) 기념 사진 생성 5) 말뚝이 진행 호스트 6) AI 가드레일(횡단)

# 7. 작성 체크리스트

- 개요만 읽어도 콘텐츠가 무엇이고 무엇을 만드는지 잡히는가
- 개요가 5항목(정의, 소재, 목표 경험, 핵심 메커닉, 산출물)만 두고, 플랫폼과 세션, 유형, 성격 불릿 없이 디바이스를 콘텐츠 정의에 흡수했는가 ([[#가. 불변식 (반드시 지킴)]] 3)
- 개요 항목에 괄호가 없는가. 약어 병기만 예외로 남겼는가 ([[#가. 불변식 (반드시 지킴)]] 4)
- 전체 플로우가 세션 흐름을 한눈에(Step 시퀀스와 이탈/실패 분기) 담고, 내부 판정 로직은 시스템 절에 두어 중복되지 않는가
- 헤딩 레벨이 [[#나. 시스템 독립 명세 양식]] 규칙과 맞는가: 공용 시스템은 H2에 명세 항목 H3, 세션 진행은 H1에 Step H2, 진행 단위 H3, 진행과 엔진 H4, 엔진 명세 H5
- 시스템이 [[#3. 표준 목차]] 정렬(공용은 콘텐츠 공용 먼저, 내부 공용 나중, 묶음 내 의존 순, 엔진은 Step 진행 순)로 배열됐는가
- 각 시스템이 [[#나. 시스템 독립 명세 양식]] 항목을 서브헤더로 두되, 필수 항목(역할과 목적/동작과 규칙)을 갖추고 조건부 항목은 해당할 때만 썼는가("해당 없음"으로 채우지 않았는가). 실패 양상이 있는 시스템에 "실패와 복구"를 빠뜨리지 않았는가. 의존 항목은 두지 않았는가
- 엔진 헤더에 "(개별 시스템)" 같은 꼬리표를 붙이지 않았는가 ([[#나. 시스템 독립 명세 양식]])
- 5. 운영 기준의 두 표가 [[#4. 시스템 작성법]]라를 따르는가: 운영 파라미터가 본문 인라인 값의 색인인가, 에러 케이스가 처리 4갈래와 원인 3분류로 전수를 덮는가
- 역할과 목적이 기능이나 동작 서술이 아니라 역할과 목적(왜 존재하나)을 담았는가
- 시스템 입도가 적절한가(한 줄로 끝나거나 서로 다른 메커닉을 한 블록에 뭉치지 않았는가)
- 프로그래머, 아티스트, 기획자가 각자 관심 줄로 바로 이동할 수 있는가
- 화면의 시각과 레이아웃 상세만 UI 문서로 갔고, 화면이 받는 입력과 판정과 상태 로직은 본문에 남았는가
- 세션, 연속성, 공통 개인정보, 공통 기술 방향은 공통 사양과 플랫폼 사양을 참조하고, 콘텐츠 고유 데이터와 개인정보, 영역별 기술 구현은 본문 시스템에 뒀는가
- 전문용어와 번역 투 없이 평이하고, 약어는 본디 용어를 병기했는가 ([[#가. 평이화 (전문용어와 번역 투 배제)]])
- 절 제목이 내용을 정확히 가리키고 같은 개념을 한 용어로 통일했는가 ([[#나. 명명 정합]])
- 표 셀과 참조가 윗행이나 외부 맥락 없이 자족적인가 ([[#다. 자족성]])
- 순차가 아닌 이벤트를 억지 순차로 넣지 않고, 반복 공통 패턴을 공통 사양으로 올렸는가 ([[#라. 구조 정합]])
- 가운뎃점과 em dash 없이 사내 실재 용어로 표기했는가 ([[#마. 표기]])
- 본문에서 타문서 링크와 참고를 걷어 관련 문서 절로 모으고, 시스템은 이름으로 평문 참조했는가. § 참조는 비-시스템 절(운영 파라미터, 에러 케이스)에만 절 번호와 이름을 함께 써서 남겼는가 ([[#나. 설계 원칙]] 참조 집약)
- 튜닝값(임계, 재시도, 타임아웃, 길이, 생성 튜닝값)을 쓰이는 지점에 실제 잠정값과 근거로 적었는가. 운영 파라미터 표에만 있고 본문에 없는 값을 두지 않았는가 ([[#나. 설계 원칙]] 튜닝값 인라인)
- 유저 입력 재시도 분기에 무한 반복을 막는 한도와 초과 처리를 넣었는가 ([[#라. 구조 정합]])
- 새로 쓰거나 고친 정본 문장이 독립 검토(서브에이전트나 Codex)를 거쳤는가 ([[#바. 낯선 독자 검토 (작성 후 점검)]])
- frontmatter status와 잠정값, 확인 필요 항목이 표기됐는가
