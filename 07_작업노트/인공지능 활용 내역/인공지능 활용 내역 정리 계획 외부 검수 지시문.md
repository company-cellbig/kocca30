> [[인공지능 활용 내역 정리 계획]]을 새 Claude Code 세션에서 검토할 때 전달하는 독립 맥락 검수 패킷임. 대상 커밋과 저장소 파일만 근거로 사실과 정합, 적대, 가독성 검토를 각각 수행하고 파일은 수정하지 않은 채 발견만 보고하도록 지시함.

# 1. 사용 방법

- 새 Claude Code 세션을 열고 이 문서의 `검수 지시문` 절부터 끝까지 전달함
- 작성 대화, 작성 의도와 중간 추론은 전달하지 않음
- Claude Code가 이 저장소와 Git 이력을 직접 읽을 수 있는 위치에서 실행함
- 검토 보고를 받은 뒤 항목별 수용, 보류와 반려는 사용자가 결정함

# 2. 검수 지시문

당신은 이 변경의 외부 검토자다. 파일을 수정하지 말고 발견만 보고하라. Git 등록, 커밋과 브랜치 조작도 하지 마라.

작성자의 의도나 중간 추론을 추정하지 말고 완성된 변경, 지정된 원자료와 저장소 규칙을 직접 대조하라. 검토 무발견은 결함 부재의 증명이 아니므로 수행 범위와 발견 건수만 보고하라. 승인, 통과와 최종 판정을 선언하지 마라.

대상 커밋만 검토하라. 현재 작업 트리의 미커밋 변경이나 대상 커밋 이후 변경은 검토 범위에 넣지 마라. 다음 명령으로 대상을 고정할 수 있음.

```powershell

```

## 2.3 기준선 사실 대조

계획 문서가 제시한 기준선은 다음과 같음.

- 기준 커밋: `130b7ab776a37e9d408ca2a4a7baf7131a44216d`
- 기준선 로그 객체: `91a1a711ee293ceafd463d7b71c1cd5501b0904c`
- 표시 행: 12,598행
- 로그 항목: 1,282건

저장소 객체를 직접 읽어 해시의 존재, 파일 내용, 행 수의 계산 방식과 로그 항목 수를 대조하라. 현재 `99_Logs/log.md`는 대상 커밋의 새 로그 항목 때문에 기준선과 다를 수 있으므로 수치 대조에 사용하지 마라.

로그 항목은 `## [날짜] 작업유형 | 제목` 형식의 같은 수준 헤딩으로 정의함. 행 수는 UTF-8 텍스트의 줄바꿈과 마지막 줄 처리 방식을 명시해 계획의 `물리 행` 표현이 모호하거나 틀리지 않은지도 판단하라.

# 3. 검토 지침

이 저장소는 마크다운 문서 저장소임. 다음 우선순위로 비판적 검수를 수행하라. `괜찮아 보임`은 사유가 아니며 결함을 적극적으로 찾아야 함. 접근할 수 없는 근거만 `검증 불가`로 보고하라.

세 검토를 한 번에 섞지 말고 `사실과 정합`, `적대`, `가독성` 순서로 각각 독립 수행한 뒤 발견도 같은 구분으로 보고하라.

## 3.1 사실과 정합

### 3.1.1 P1 사실 오류와 출처 불일치

- 수치, 일정과 인용이 지정된 원자료와 일치하는가
- 출처 없이 들어간 정량 주장이 있는가
- 기준 커밋, 로그 객체, 행 수, 항목 수와 예상 묶음 수를 직접 재계산했을 때 일치하는가
- 사실이 아닌 설계 선택을 원자료에서 나온 유일한 사실처럼 표현하지 않았는가

### 3.1.2 P5 위키 정합성

- 참조가 실제로 그 내용을 담은 곳을 가리키는가
- 계획이 예고한 세 후속 문서의 역할이 겹치거나 서로 상세를 미루는 빈 참조가 되지 않는가
- MOC 설명, 계획 문서의 목적과 로그 요약이 서로 일치하는가
- 깨진 링크, 헤딩 번호와 MOC 등록의 기계 검사는 이번 검토에서 반복하지 말고 의미 정합만 봐라

## 3.2 적대

### 3.2.1 P2 논리적 비약과 추론 정정

- `로그 항목`, `활용 사건`과 `결과물`이 서로 다른 단위로 일관되게 구별되는가
- 묶음 상한, 권장 행 수, 예상 묶음 수와 전체 항목 수 사이에 산술 또는 운영 모순이 없는가
- 오래된 항목부터 읽는 순서가 생성, 수정, 대체와 폐기 관계를 보존하는가
- 기준선 고정과 변경분 별도 처리 방식이 분석 도중 추가된 로그를 누락하거나 중복시키지 않는가
- 원시 목록을 완성하기 전에 결과물 분류를 확정하지 않는 절차가 실제 완료 조건까지 유지되는가
- 한 로그 항목에서 여러 결과물이 나오거나 여러 로그 항목이 같은 결과물을 갱신할 때 대응 관계를 잃지 않는가

### 3.2.2 P3 누락된 반론과 견고성

- 로그에 인공지능 사용 여부가 명시되지 않은 항목을 포함 또는 제외하는 기준이 충분한가
- 문서 작성, 코드 작성, 검수와 기계 실행을 구분하지 못해 인공지능 활용을 과대 또는 과소 집계할 가능성이 남아 있지 않은가
- 파일로 남지 않은 분석과 자문, 하나의 파일 안에 섞인 여러 결과물, 삭제된 결과물과 경로가 바뀐 결과물을 다룰 수 있는가
- `확인 필요` 항목을 최종 보고에서 잃지 않는 장치가 있는가
- 기준선 로그가 바뀌거나 Git 객체에 접근할 수 없을 때의 한계와 복구 절차가 필요한가

### 3.2.3 반복 결함 우선 점검

`01_HowTo/반복 결함 카탈로그.md` 본문 전체를 읽고 대상 변경에서 재발한 항목을 우선 찾아라. 특히 다음 결함류를 주의하되 여기에만 한정하지 마라.

- `STRUCT-002`, `STRUCT-003`, `STRUCT-005`: 서로 다른 종류나 위계의 항목을 같은 표와 목록에 섞음
- `CONTENT-001`: 파일 형식이 같다는 이유로 역할이 다른 결과물을 혼동함
- `CONTENT-002`: 이름과 한 줄 라벨만 있고 역할, 입력, 출력이나 용도가 없음
- `STRUCT-008`, `STRUCT-009`: 한 불릿에 복수 항목을 넣거나 정보에 맞지 않는 목록 형식을 선택함
- `PROCESS-001`: 일부 사례만 고치고 같은 결함류의 나머지를 놓침
- `PROCESS-002`: 목표 개수나 분류를 먼저 정하고 원자료를 끼워 맞춤

## 3.3 가독성

맥락 없는 독자로 각 문장을 읽고 다음을 적극 지적하라.

- 정의하지 않은 용어나 지시어
- 구어체, 비표준어와 임의 조어
- 같은 뜻을 다른 문장으로 반복하는 군더더기
- 단순 문장 나열과 의미 분류 부족
- 한 단계 불릿에 역할, 단계나 종류가 여러 개 들어간 구조
- 조건과 결과인데 평문으로 쓴 경우 등 목록 형식 오선택
- 같은 수준 항목의 문법 형태가 다른 비병렬 구조
- `내용`, `기타`와 `참고`처럼 정보가 없는 항목명
- 음슴체, 가운뎃점, em dash와 슬래시 절제 위반
- `기준선`, `로그 객체`, `물리 행`, `사건 ID`, `결과물 ID`를 처음 보는 개발자나 심사자가 한 번에 이해할 수 있는가

# 4. 출력 형식

발견은 `사실과 정합`, `적대`, `가독성` 세 절로 나눠 다음 표에 작성하라. 발견이 없으면 해당 절에 수행 범위와 `0건`만 적어라.

| ID | 우선순위 | 위치 | 문제 | 근거 | 영향 | 제안 | 근거 등급 |
|---|---|---|---|---|---|---|---|
| 예: F-01 | P1 | 파일명:행 | 무엇이 틀리거나 모호한지 | 직접 대조한 파일과 위치 | 그대로 둘 때 생기는 문제 | 최소 정정안 | L1~L5 또는 해당 없음 |

- 위치는 `파일명:행`으로 적고 가능하면 대상 문구를 짧게 병기함
- 근거는 직접 확인한 저장소 파일, Git 객체와 행을 적음
- 근거가 약하면 `근거 약함`을 표시하고 L1~L5 중 등급을 적음
- 같은 원인의 반복은 대표 발견 아래 모든 위치를 나열함
- 수정안을 제안할 수 있으나 파일에는 반영하지 않음
- 발견의 수용, 보류와 반려를 결정하지 않음

마지막에는 다음 요약만 덧붙여라.

- 검토한 커밋과 파일
- 세 검토별 발견 건수
- 검증하지 못한 범위와 이유
- 반복 결함 카탈로그에서 대조한 항목

# 5. 금지 사항

- 작성 의도와 중간 추론을 추정하지 않음
- 현재 작업 트리의 미커밋 변경을 검토하지 않음
- 파일과 로그를 수정하지 않음
- Git 등록, 커밋, 전송과 브랜치 조작을 하지 않음
- 발견을 자동 반영하지 않음
- 승인, 통과와 최종 판정을 선언하지 않음
