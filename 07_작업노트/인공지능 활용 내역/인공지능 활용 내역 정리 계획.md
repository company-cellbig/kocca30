> `99_Logs/log.md`의 로그 항목을 처리 단계별로 나누어 읽고, 항목 안에서 인공지능 활용 사건을 추출한 뒤 결과물 이력으로 통합하는 절차임. 처리 현황을 범위와 진행 상태의 정본으로 삼고 채팅에는 그 내용을 발췌해 보고함.

# 1. 목적과 산출물

- **목적**: 과제 수행 중 인공지능이 내용, 코드, 매체, 분석이나 검수에 실질적으로 기여한 작업과 결과물을 근거가 남는 목록으로 정리함
- **원칙**: 로그 항목을 먼저 전수 처리해 원시 목록을 완성하고, 결과물 분류는 그 목록을 근거로 확정함
- **산출물**
	- `07_작업노트/인공지능 활용 내역/인공지능 활용 내역 처리 현황.md`: 기준선, 묶음 범위, 처리 단계와 개수의 정본
	- `07_작업노트/인공지능 활용 내역/인공지능 활용 내역 원시 목록.md`: 로그 항목에서 나눈 활용 사건과 판정 근거
	- `07_작업노트/인공지능 활용 내역/인공지능 활용 결과물 분류.md`: 같은 결과물의 생성과 수정을 통합한 보고 목록

# 2. 용어와 분석 범위

## 2.1 용어

| 용어 | 뜻 |
|---|---|
| 계획 기준선 | 이 계획을 만들 때 규모를 가늠하려고 고정한 로그 객체 |
| 착수 기준선 | 실제 목록 작성 직전에 고정하며 원문 위치와 처리 개수의 기준이 되는 로그 객체 |
| 로그 항목 | `## [날짜] 작업유형 \| 제목` 헤딩부터 다음에 나오는 같은 수준의 헤딩 직전까지의 원문 단위 ([[CONVENTIONS#7. 로그 항목 양식]]) |
| 활용 사건 | 로그 항목 안에서 구별되는 인공지능 활용 작업 하나. 한 로그 항목에서 없거나 여러 개 나올 수 있음 |
| 결과물 | 하나 이상의 활용 사건으로 만들어지거나 수정된 보고 대상 문서, 매체, 프로그램이나 데이터 |
| 결과물 키 | 경로 이동과 이름 변경 전후의 같은 결과물을 연결하는 임시 식별값 |
| 처리 단계 | `색인`, `읽음`, `추출`, `대조`로 구분하는 묶음 진행 상태 |

## 2.2 원자료와 한계

- **주 원자료**: `99_Logs/log.md`
- **보조 근거**
	- 저장소의 현행 파일과 Git 이력
	- 사용자가 알려 준 저장소 밖 결과물과 사용 내역
- **범위 한계**: 로그에 적히지 않았고 사용자가 별도로 알려 주지 않은 인공지능 사용은 목록에 포함할 수 없음. 저장소 밖 결과물은 사용자 제보로 후보에 넣고 경로와 실체를 확인하기 전까지 `확인 필요`로 둠
- **인공지능 활용 판정**: 인공지능이 내용 생성, 구조 설계, 분석, 코딩, 매체 생성, 수정이나 검수에 실질적으로 기여했는지를 봄. 단순히 로그에 기록됐다는 이유만으로 모두 포함하지 않음

## 2.4 착수 기준선과 종료 규칙

- 실제 목록 작성 직전에 최신 커밋, 로그 객체, 본문 줄 수와 로그 항목 수를 `인공지능 활용 내역 처리 현황.md`에 다시 기록함
- 분석 중 `log.md`가 바뀌어도 착수 기준선의 원문 위치와 사건 ID는 바꾸지 않음
- 착수 기준선 처리를 끝내면 착수 기준선과 종료 시점 사이의 `log.md` 객체 차이를 Git으로 대조해 새 항목을 한 차례만 추가 처리함
- 추가 처리와 결과 정리 때문에 다시 생긴 로그 항목은 이번 범위에 되먹이지 않고 다음 갱신 대상으로 넘김

# 3. 읽기 방향과 처리 단위

## 3.1 읽기 방향

`log.md`는 최신 항목이 위에 쌓이는 역순 문서임. 결과물의 생성과 변경을 누적하기 위해 착수 기준선의 마지막 로그 항목부터 첫 로그 항목까지 파일의 물리 순서를 거꾸로 읽음.

- 같은 날짜의 항목도 날짜만으로 다시 정렬하지 않고 파일 안 위치를 거꾸로 따라감
- 날짜 순서가 어긋난 항목이 있어도 원문 위치를 보존하고 임의로 옮기지 않음
- `첫 항목`과 `마지막 항목`은 파일 위치인지 처리 순서인지 함께 적어 뜻이 갈리지 않게 함

## 3.2 묶음 경계

- **결정 기준**: 로그 항목 최대 80건을 한 묶음으로 삼음
- **참고값**: 묶음의 줄 수는 항목 길이에 따라 달라지므로 목표나 통과 기준으로 쓰지 않음
- **경계 원칙**: [[CONVENTIONS#4.2 헤딩 넘버링|로그 헤딩]]을 경계로 삼고 한 로그 항목의 본문을 중간에서 자르지 않음
- **계획 기준선 예상값**: 1,282건을 최대 80건씩 나누면 17개 묶음임
- **착수 시 재계산**: 실제 묶음 수는 착수 기준선 항목 수를 80으로 나누어 올림함

# 4. 원시 목록 작성

## 4.1 기록 단위와 ID

- 착수 기준선의 로그 항목마다 처리 순서에 따라 오래된 항목부터 `L0001` 형식의 로그 항목 ID를 붙임
- 로그 항목에서 활용 작업을 나누어 `L0001-01`, `L0001-02` 형식의 사건 ID를 붙임
- 한 로그 항목에서 활용 사건이 나오지 않으면 원시 목록에 억지로 빈 사건을 만들지 않고 처리 현황에 무사건 사유를 기록함
- 원시 목록 한 행은 활용 사건 하나이며 결과물 하나와 반드시 일대일일 필요는 없음

## 4.2 기록 항목

| 필드 | 기록 내용 |
|---|---|
| 로그 항목 ID | 사건이 나온 원문 항목의 ID |
| 사건 ID | 활용 사건의 고유 번호 |
| 날짜 | 원문에 적힌 작업 날짜 |
| 원문 위치 | 착수 기준선에서 해당 로그 항목 원문의 시작 행과 종료 행 |
| 로그 제목 | 항목 헤딩 원문 |
| 활용 작업 | 인공지능을 이용해 수행한 일 |
| 인공지능 활용 근거 | 도구명, 에이전트 작업 기록, 사용자 제보 등 판정에 쓴 근거 |
| 결과물명 | 생성하거나 수정한 파일 또는 결과물 이름 |
| 당시 경로 | 로그에 기록된 시점의 경로 |
| 현재 경로 | 현행 파일이나 Git 이력으로 확인한 경로 |
| 결과물 키 | 같은 결과물의 다른 사건을 연결하는 임시 값 |
| 판정 | 포함, 제외 또는 확인 필요 |
| 판정 사유 | 포함 근거, 제외 사유 또는 확인할 사항 |
| 관련 사건 ID | 같은 결과물을 생성, 수정, 재생성하거나 폐기한 원시 목록 사건 ID |

## 4.3 포함 기준

- 문서의 내용이나 구조 작성과 갱신
- 조사와 분석 결과 작성
- 이미지 생성과 수정
- 영상 생성과 수정
- 음원과 음성 생성 또는 수정
- 웹 프로토타입과 응용 프로그램 제작
- 업무지원 도구와 자동화 스크립트 제작
- JSON 등의 구조화 데이터 제작과 변환
- 검수, 오류 탐색과 정합성 보정 결과 작성
- 인공지능이 제안하거나 구현한 설계 변경
- 기계적 작업을 수행하기 위해 인공지능이 새로 제작한 도구나 스크립트

## 4.4 제외 기준

- Git 등록, 커밋과 전송만 수행하고 별도 내용이나 결과물을 만들지 않은 사건
- 기존 검사 도구를 실행하기만 하고 별도 분석 결과를 만들지 않은 사건
- 파일 이동, 이름 변경이나 삭제만 수행하고 내용 판단이나 변환이 없는 사건
- 결과물 통합 단계의 전역 대조에서 앞선 활용 사건을 내용 추가 없이 되풀이한 것으로 확정된 기록

제외 사건도 원시 목록에서 지우지 않고 제외 사유를 기록함. 한 로그 항목에 포함 사건과 제외 사건이 함께 있으면 각각 나누어 기록함.

**중복 후보 처리**: 원시 추출 때 중복으로 보이는 사건은 `확인 필요`로 두고 결과물 통합 단계의 전역 대조에서 포함 또는 제외로 확정함.

## 4.5 근거 수준과 확인 필요 처리

- **명시 근거**: 로그에 인공지능 도구명이나 생성 행위가 직접 적힘
- **운영 근거**: [[AGENTS#2.1 역할 분담|에이전트 작업 흐름]]과 로그 내용으로 인공지능 기여를 확인할 수 있음
- **사용자 제보**: 사용자가 저장소 밖 결과물의 존재와 인공지능 사용을 알려 줌
- **확인 필요**: 확보한 근거만으로 결과물의 실체, 현재 경로나 인공지능 기여 중 하나 이상을 확정할 수 없음

확인 필요 사건은 저장소 파일과 Git 이력을 먼저 대조하고, 해소되지 않으면 사용자에게 묻는 순서로 처리함. 답을 받기 전에는 별도 확인 필요 목록에 남기며 최종 결과물 수에 억지로 넣지 않음.

사용자가 알려 준 C# JSON 변환 도구는 로그 밖 후보로 원시 목록에 추가하되, 현재 경로와 실체를 확인하기 전까지 사용자 제보 근거의 `확인 필요`로 둠.

# 5. 묶음별 작업 절차

1. 착수 기준선 전체의 로그 헤딩과 원문 위치를 색인하고 처리 현황을 `색인`으로 기록함
2. 묶음 안의 로그 항목 본문을 모두 읽고 처리 현황을 `읽음`으로 바꿈
3. 각 로그 항목에서 활용 사건을 식별해 하나 이상이면 원시 목록에 기록하고, 없으면 무사건 항목 ID와 사유를 기록함. 묶음 안의 모든 로그 항목을 이렇게 처리한 뒤 묶음의 처리 단계를 `추출`로 바꿈
4. 원문 헤딩 수와 처리 항목 수가 같은지 대조하고, 모든 로그 항목이 사건 ID 또는 무사건 사유를 가지는지 확인함
5. 사건 ID 중복, 판정별 개수와 다음 범위를 확인한 뒤 `대조`로 바꿈
6. 처리 현황의 해당 묶음 행을 채팅에 발췌해 보고함

# 6. 진행 보고

묶음이 끝날 때마다 다음 내용을 처리 현황 문서에서 가져와 채팅에 보고함. 전체 묶음의 `대조`가 끝나기 전에는 `전체 확인`이나 `완독`으로 표현하지 않음.

- 현재 묶음 ID와 착수 기준선의 전체 묶음 수
- 처리 단계
- 로그 항목 ID와 원문 위치
- 원문 헤딩 수, 처리 항목 수, 활용 사건 수와 무사건 항목 수
- 포함, 제외와 확인 필요 사건 수
- 누적 처리 항목 수와 착수 기준선 전체 항목 수
- 다음에 읽을 로그 항목 ID와 원문 위치

# 7. 원시 목록 완성 조건

- 처리한 로그 항목 ID 수가 착수 기준선의 로그 항목 수와 같음
- 처리 순서의 첫 항목과 마지막 항목이 모두 처리됨
- 묶음 사이의 로그 항목 ID와 원문 위치에 빈 구간이 없음
- 같은 로그 항목 ID나 사건 ID가 중복되지 않음
- 각 로그 항목이 하나 이상의 사건 ID 또는 무사건 사유를 가짐
- 묶음마다 원문 헤딩 수와 처리 항목 수가 같음
- 포함, 제외와 확인 필요 사건 수의 합이 원시 목록의 전체 사건 수와 같음
- 모든 묶음의 처리 단계가 `대조`임
- 착수 기준선과 종료 시점 사이의 `log.md` 객체 차이를 Git으로 대조해 한 차례 추가 처리함

이 조건을 모두 충족한 뒤에만 `착수 기준선 로그 전체 1회 처리`로 보고함. 전수 처리 사실을 내용의 무오류로 확대해 표현하지 않음.

# 8. 결과물 통합

원시 목록을 완성한 뒤 결과물 키를 전역 대조함. 원시 목록의 한 행은 활용 사건이고 최종 보고의 한 행은 결과물임.

- 파일 경로와 이름이 같으면 같은 결과물 후보로 묶음
- Git rename 이력과 로그의 이동 기록을 확인해 경로가 바뀐 같은 파일을 연결함
- 이름이 바뀌어도 기능과 이력이 이어지면 통합 후보로 표시하고 합친 근거를 기록함
- 한 로그 항목이 여러 결과물을 만들었으면 사건을 결과물별로 나눔
- 한 사건이 여러 파일로 구성된 결과물 하나를 만들었으면 하나의 결과물 키와 구성 파일 목록을 사용함
- 폐기되거나 대체된 결과물도 삭제하지 않고 결과물 생명주기 상태를 표시함
- 중복 기록은 이 단계에서 전체 원시 목록을 대조해 `확인 필요` 판정을 포함 또는 제외로 확정함
- 통합 전 사건 ID와 통합 후 결과물 ID의 대응표를 남김

# 9. 결과물 분류

다음 분류는 착수 전 후보이며 원시 목록을 먼저 완성한 뒤 근거에 따라 추가, 병합, 이름 변경이나 폐기할 수 있음. 매체 형식은 대분류, 구체 용도는 세부 분류, 인공지능이 한 일은 별도 활용 방식 필드로 나눔.

## 9.1 후보 대분류

| 대분류 | 정의 | 대표 세부 분류 | 인접 분류와 경계 |
|---|---|---|---|
| 문서 | 사람이 읽는 글, 표나 발표 자료가 중심인 결과물 | 기획서, 조사서, 시나리오, 발표자료, 검수 보고 | 실행 동작이 중심이면 소프트웨어, 기계 처리가 중심이면 데이터로 분류함 |
| 이미지 | 한 화면의 정지 시각물이 중심인 결과물 | 콘셉트 아트, 배경, 캐릭터, UI 시안 | 시간축이 있으면 영상, 입체 모델이면 3D 자산으로 분류함 |
| 영상 | 시간축을 따라 재생되는 시각물이 중심인 결과물 | 생성 영상, 시연 영상, 편집 영상 | 소리만 있으면 음원과 음성으로 분류함 |
| 음원과 음성 | 소리 재생이 중심인 결과물 | 배경음악, 효과음, 내레이션 | 영상 파일의 부속 음향은 영상의 구성 요소로 기록함 |
| 소프트웨어 | 실행, 상호작용이나 자동 처리를 수행하는 코드 결과물 | 인터랙티브 웹 프로토타입, C# 업무지원 도구, 자동화 스크립트 | 프로그램이 읽는 값 자체는 데이터로 분류함 |
| 데이터 | 프로그램이 읽고 쓰는 구조화 값이 중심인 결과물 | JSON, CSV, 설정값, 변환 데이터 | 데이터를 만드는 변환 프로그램은 소프트웨어로 분류함 |
| 3D 자산 | 입체 형상, 골격, 동작이나 공간 자산이 중심인 결과물 | 모델, 리깅, 애니메이션, 공간 구성 | 렌더링한 정지 화면은 이미지, 재생 영상은 영상으로 분류함 |

여러 형식이 묶인 결과물은 사용 목적의 중심이 되는 대분류 하나를 선택하고 구성 파일을 별도 기록함. 대분류를 정할 근거가 부족한 사건은 `분류 미정` 목록에 남기며 `기타`를 대분류로 만들지 않음.

## 9.2 별도 분류 필드

- **세부 분류**: 기획서, 웹 프로토타입, 변환 도구처럼 같은 대분류 안의 용도
- **인공지능 활용 방식**: 생성, 분석, 코딩, 수정, 검수 등 인공지능이 수행한 일
- **활용 목적**: 과제에서 결과물이 맡은 기능

HTML 프로토타입은 소프트웨어의 `인터랙티브 웹 프로토타입`, C# JSON 변환 도구는 소프트웨어의 `업무지원 변환 도구`, 변환된 JSON은 데이터의 `변환 데이터` 후보로 구분함.

# 10. 최종 보고 항목

| 필드 | 기록 내용 |
|---|---|
| 결과물 ID | 통합 결과물의 고유 번호 |
| 결과물명 | 보고용 이름 |
| 대분류 | 문서, 이미지, 영상, 음원과 음성, 소프트웨어, 데이터 또는 3D 자산 |
| 세부 분류 | 기획서, 웹 프로토타입, 변환 도구 등 |
| 활용 목적 | 과제에서 맡은 기능 |
| 구현 형식 | Markdown, PNG, HTML, C#, JSON 등 |
| 인공지능 활용 방식 | 생성, 분석, 코딩, 수정, 검수 등 |
| 근거 출처 | 로그, Git, 현행 파일이나 사용자 제보 |
| 관련 사건 ID | 원시 목록에서 이 결과물과 연결된 사건 ID 목록 |
| 최초 경로 | 처음 확인된 파일이나 저장 위치 |
| 현재 경로 | 현행 파일이나 저장 위치 |
| 결과물 생명주기 상태 | 현행, 수정 중, 대체 또는 폐기 |
| 확인 사항 | 근거 부족이나 사용자 확인이 필요한 내용 |

근거 부족으로 결과물 ID를 부여할 수 없는 확인 필요 사건은 별도 목록으로 최종 보고에 붙임.

# 11. 완료 기준

- 원시 목록의 전수 처리 조건을 충족함
- 모든 포함 사건이 하나 이상의 결과물 ID에 대응함
- 제외 사건은 제외 사유를 가짐
- 확인 필요 사건은 결과물 목록 또는 별도 확인 필요 목록에 남음
- 이름 변경과 경로 이동을 포함해 결과물 통합 근거를 기록함
- 결과물 통합 전후 대응표와 합친 이유를 남김
- 분류별 개수와 전체 결과물 수를 원시 목록에서 다시 계산할 수 있음
- 사용자 검토를 거쳐 보고 범위와 후보 분류의 최종 이름을 확정함
