> `99_Logs/log.md`를 빠짐없이 나누어 읽고 인공지능 활용 사건의 원시 목록을 먼저 만든 뒤, 같은 결과물의 생성과 수정을 묶어 결과물 종류별 보고 목록으로 정리하는 절차임. 기계 색인과 내용 검토를 구분하고 처리 범위와 개수를 묶음마다 기록해 완독 여부를 확인함.

# 1. 목적과 산출물

- **목적**: 과제 수행 중 인공지능을 사용한 작업과 그 결과물을 근거가 남는 목록으로 정리함
- **원칙**: 로그 항목을 먼저 전수 목록화하고, 결과물 분류는 원시 목록이 완성된 뒤 시작함
- **산출물**
	- `인공지능 활용 내역 처리 현황.md`: 분석 기준선, 묶음 범위와 처리 상태
	- `인공지능 활용 내역 원시 목록.md`: 로그 항목별 활용 사건과 포함 판정
	- `인공지능 활용 결과물 분류.md`: 같은 결과물의 생성과 수정을 통합한 최종 분류

# 2. 분석 기준선과 범위

- **원자료**: `99_Logs/log.md`
- **계획 수립 기준선**
	- Git 커밋: `130b7ab776a37e9d408ca2a4a7baf7131a44216d`
	- 로그 객체: `91a1a711ee293ceafd463d7b71c1cd5501b0904c`
	- UTF-8 물리 행: 12,598행
	- 로그 항목: 1,282건
- **착수 시 재고정**: 실제 목록 작성 직전에 최신 커밋과 로그 객체, 물리 행 수, 항목 수를 다시 기록함
- **변경 처리**: 분석 중 로그가 바뀌면 최초 기준선을 끝까지 처리한 뒤 추가되거나 달라진 항목만 별도 묶음으로 처리함
- **처리 순서**: 오래된 항목부터 최신 항목까지 시간순으로 읽어 결과물의 생성, 수정, 폐기 관계를 누적함

# 3. 처리 단위

고정 행 수로 자르면 하나의 로그 항목이 둘로 갈릴 수 있으므로 `## [날짜] 작업유형 | 제목` 헤딩부터 다음 같은 수준 헤딩 직전까지를 한 단위로 삼음.

- **묶음 상한**: 로그 항목 80건
- **권장 분량**: 물리 행 약 800~1,000행
- **경계 원칙**: 권장 분량을 넘더라도 로그 항목 본문을 중간에서 자르지 않음
- **예상 묶음**: 계획 수립 기준선에서는 약 16개임. 착수 시 항목 수에 따라 다시 계산함
- **상태 구분**
	- `색인`: 헤딩, 행 범위와 개수만 기계적으로 확인한 상태
	- `읽음`: 묶음 안의 모든 로그 항목 본문을 읽은 상태
	- `추출`: 읽은 항목을 원시 목록에 옮기고 포함 판정까지 기록한 상태
	- `대조`: 범위, 개수, 중복과 누락 검사를 마친 상태

# 4. 원시 목록 작성

## 4.1 기록 항목

| 필드 | 기록 내용 |
|---|---|
| 사건 ID | 로그 항목마다 붙이는 고유 번호 |
| 날짜 | 작업 날짜 |
| 원문 위치 | 기준선 로그의 시작 행과 종료 행 |
| 로그 제목 | 항목 헤딩 원문 |
| 작업 내용 | 인공지능을 이용해 수행한 일 |
| 생성 또는 수정 결과물 | 파일이나 결과물 이름 |
| 결과물 경로 | 로그에 기록된 경로 |
| 활용 근거 | 생성, 작성, 분석, 코딩, 검수 등 로그에서 확인한 표현 |
| 판정 | 포함, 제외, 확인 필요 |
| 관련 사건 ID | 같은 결과물의 생성, 수정, 재생성과 폐기 기록 |

## 4.2 포함 기준

- 문서 초안 작성과 내용 갱신
- 조사, 분석과 구조 설계
- 이미지, 영상과 음원 생성 또는 수정
- 웹 기반 인터랙티브 프로토타입 제작
- C#, Python, JavaScript 등의 프로그램과 자동화 도구 제작
- JSON 등의 구조화 데이터 제작과 변환
- 검수, 오류 탐색과 정합성 보정
- 인공지능이 제안하거나 구현한 설계 변경

## 4.3 제외와 보류 기준

- **제외**
	- Git 등록, 커밋과 전송만 수행한 기록
	- 기존 검사 도구를 실행하기만 한 기록
	- 파일 이동, 이름 변경과 삭제만 수행한 기록
	- 같은 활용 사건을 내용 추가 없이 다시 적은 기록
- **예외**: 기계적 작업을 수행하려고 인공지능이 새 도구나 스크립트를 제작했다면 그 도구는 결과물로 포함함
- **확인 필요**: 로그만으로 인공지능의 기여나 결과물의 실체를 판단할 수 없는 항목은 추정하지 않고 보류함

# 5. 묶음별 작업 절차

1. 기준선 로그에서 묶음의 첫 항목, 마지막 항목과 물리 행 범위를 확정함
2. 묶음 안의 로그 항목 본문을 처음부터 끝까지 읽음
3. 항목별 활용 사건을 원시 목록에 옮기고 포함, 제외 또는 확인 필요로 판정함
4. 같은 결과물의 앞선 사건 ID를 연결하되 이 단계에서는 하나로 합치지 않음
5. 처리 현황에 묶음 범위, 항목 수, 판정별 개수와 다음 범위를 기록함
6. 묶음 범위의 첫 헤딩과 마지막 헤딩을 원문과 다시 대조함

# 6. 진행 보고

묶음이 끝날 때마다 다음 정보를 채팅에 보고함. 전체 묶음이 끝나기 전에는 `전체 확인`이나 `완독`으로 표현하지 않음.

- 현재 묶음 번호와 전체 예상 묶음 수
- 처리한 사건 ID와 원문 행 범위
- 이번 묶음의 포함, 제외와 확인 필요 개수
- 누적 처리 항목 수와 기준선 전체 항목 수
- 다음에 읽을 사건 ID와 원문 행 범위

# 7. 원시 목록 완성 조건

- 처리한 사건 ID 수가 기준선의 로그 항목 수와 같음
- 최초 항목과 최종 항목이 모두 포함됨
- 묶음 사이의 행 범위와 사건 ID에 빈 구간이 없음
- 같은 사건 ID가 둘 이상의 묶음에 중복되지 않음
- 포함, 제외와 확인 필요 개수의 합이 전체 항목 수와 같음
- 착수 기준선과 종료 시점의 로그 객체를 비교하고 변경분을 별도 처리함

이 조건을 모두 대조한 뒤에만 `기준선 로그 전체 1회 처리`로 보고함. 무발견이나 전수 처리 사실을 내용의 무오류로 확대해 표현하지 않음.

# 8. 결과물 통합과 분류

원시 목록의 한 행은 작업 사건이고 최종 보고의 한 행은 결과물임. 같은 파일이나 기능의 생성, 수정, 재생성과 폐기는 관련 사건 ID를 보존하면서 하나의 결과물 이력으로 통합함.

## 8.1 통합 규칙

- 파일 경로와 결과물 이름이 같으면 같은 결과물 후보로 묶음
- 이름이 달라도 기능과 계보가 같으면 통합 후보로 표시하고 합친 이유를 기록함
- 한 로그 항목이 서로 다른 결과물을 만들었으면 결과물별로 나눔
- 폐기되거나 대체된 결과물도 삭제하지 않고 현재 상태를 표시함
- 통합 전 사건 ID와 통합 후 결과물 ID의 대응표를 남김

## 8.2 결과물 분류안

- 문서
- 이미지
- 영상
- 음원과 음성
- 프로그램과 업무지원 도구
- 인터랙티브 웹 프로토타입
- 데이터와 JSON
- 3D와 실감형 자산
- 분석과 검수 결과
- 기타 또는 확인 필요

결과물 종류와 인공지능 활용 방식을 분리해 기록함. 예를 들어 HTML 프로토타입은 `인터랙티브 웹 프로토타입`, C# JSON 변환 도구는 `프로그램과 업무지원 도구`, 변환된 JSON은 `데이터와 JSON`으로 분류함.

# 9. 최종 보고 항목

| 필드 | 기록 내용 |
|---|---|
| 결과물 ID | 통합 결과물의 고유 번호 |
| 결과물명 | 보고용 이름 |
| 대분류 | 문서, 이미지, 프로그램 등 |
| 세부 분류 | 기획서, 웹 프로토타입, 변환 도구 등 |
| 활용 목적 | 과제에서 맡은 기능 |
| 구현 형식 | Markdown, PNG, HTML, C#, JSON 등 |
| 인공지능 활용 방식 | 생성, 분석, 코딩, 수정, 검수 등 |
| 관련 사건 ID | 원시 목록의 근거 행 |
| 현재 상태 | 현행, 수정 중, 대체 또는 폐기 |
| 확인 사항 | 근거 부족이나 사용자 확인이 필요한 내용 |

# 10. 완료 기준

- 원시 목록의 전수 처리 조건을 충족함
- 모든 포함 사건이 하나 이상의 결과물 ID에 대응함
- 제외 사건은 제외 사유를 가짐
- 확인 필요 사건은 최종 보고에서 누락하지 않고 별도 표시함
- 결과물 통합 전후 대응표와 합친 이유를 남김
- 분류별 개수와 전체 결과물 수를 원시 목록에서 다시 계산할 수 있음
- 사용자 검토를 거쳐 보고 범위와 분류명을 확정함
